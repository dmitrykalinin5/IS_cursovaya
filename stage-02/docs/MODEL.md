# Модель данных «ЛабРезерв»

Дата: 09.11.2026. Основа — согласованные `../ER-модель_final.drawio.xml/png` и текущая даталогическая `../diagrams/logical.xml`.

## Точное соответствие

13 сущностей + две связующие таблицы M:N = **15 таблиц PostgreSQL**. Дополнительных таблиц нет.

- app_user — Пользователь; app_role — Роль; user_role — назначение ролей M:N.
- equipment_type — Тип оборудования; capability — Функция оборудования; type_capability — поддержка функций M:N.
- equipment — Единица оборудования; admission — Допуск.
- booking — Бронирование; alternative — Предложение переноса; use_session — Сеанс использования.
- notification — Уведомление; fault_report — Сообщение о неисправности.
- unavailability — Техническое событие; repair — Техническая работа.

Префикс lr_ на Helios отделяет наши объекты от других работ. Он не меняет состав модели.

Отдельные сущности аудита и конфликта исключены по прямому уточнению пользователя. История хранится в самих бронях, предложениях, сообщениях, технических событиях, работах и сеансах; терминальные записи защищены от удаления/перезаписи. Общего журнала старых/новых значений нет. Причина отказа возвращается через SQLSTATE либо request_booking, но не сохраняется отдельной строкой. Аналитика возвращает плановую и фактическую загрузку, технический простой и процент утилизации; накопленной статистики отказов нет. Уточнение заменяет прежнюю реализацию общего аудита FR-24 и соответствующей части FR-22.

Сведения об установке хранятся в комментарии к lr_app_user, а не в отдельной таблице. Это метаданные PostgreSQL, не атрибут предметной сущности.

## Ключи и нормализация

24 FK, все ON DELETE RESTRICT / ON UPDATE RESTRICT. Справочные названия не копируются в операции; M:N реализованы составными PK. Схема ориентирована на 3НФ. JSONB используется только для характеристик аппарата. schedule_revision — технический счётчик сериализации.

Одна бронь имеет одного владельца, аппарат и требуемую функцию; 0..1 фактический сеанс. Один сеанс на бронь обеспечен UNIQUE. Один тип может иметь много аппаратов, у аппарата ровно один тип. Функции задаются типом.

У сообщения 0..1 техническое событие. При kind=fault ссылка на подтверждённое сообщение обязательна, при maintenance запрещена. Уведомление имеет одного получателя и необязательную бронь. У работы один исполнитель; work_kind обязателен. При закрытии события фиксируется maintenance либо repair.

## Интервалы и операции

Моменты — timestamptz; отображение Europe/Moscow. Домен time_window использует tstzrange, непустые интервалы [начало, конец), конечное начало. Для брони, предложения и работы конец конечен; у поломки конец может быть неизвестен. Допуск покрывает весь интервал.

Подтверждённые брони не пересекаются. ТО и неисправности блокируют новые брони; будущие затронутые брони получают needs_transfer. Выбор переноса явный, слоты проверяются повторно. После ремонта переносимые брони не подтверждаются сами. Сеанс закрывается единожды; административное закрытие требует комментария.

Техническое состояние вычисляется по архивированию и техническим событиям. Простой рассчитывается объединением интервалов без двойного счёта; фактическая загрузка отделена от плановой. Полные контракты — FUNCTIONS.md; словарь — DATA_DICTIONARY.md.
