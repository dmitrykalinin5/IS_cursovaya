# Целостность, транзакции и граница доверия

## Декларативные инварианты

- PK и UNIQUE: идентичность, логины, инвентарные номера, связующие пары, один сеанс на бронь, одна подтверждённая недоступность на сообщение.
- 27 FK с RESTRICT: отсутствие сирот и удалений связанных исторических объектов.
- `time_window` и CHECK: непустые полуоткрытые интервалы, конечные обязательные границы, перечисления состояний, согласованность отмены/закрытия с метаданными.
- `ex_booking_overlap`: составной частичный GiST по оборудованию и диапазону, только `status=confirmed`.
- `ux_notification_reminder`: одно напоминание на бронь; повторный запуск безопасен.

## Триггеры

`booking_guard`: активность пользователя, допуск на весь интервал, функция и архив каталога, отсутствие недоступности, неизменность владельца/функции, терминальная история и ограничения при существующем сеансе.
`unavailability_guard`: Техник или Администратор, соответствие подтверждённого сообщения оборудованию, неизменность закрытой истории.
`unavailability_impact`: будущие пересекающиеся брони → needs_transfer, уведомление и подбор вариантов в одной транзакции.
`session_guard`, `session_complete`: подтверждённая бронь, актуальная активность/допуск/доступность и попадание начала в плановый интервал; единственное закрытие и статус completed.
`repair_guard`, `fault_guard`: исполнитель технической работы и история проверки сообщения.
`audit_immutable`, `conflict_immutable`, `repair_immutable`, `fault_no_delete`, `admission_guard`: сохранение истории.
13 `audit_*`: JSONB до/после, автор, txid, время. Изменение одного технического schedule_revision не засоряет аудит; хеш пароля исключён из снимков.
Полный перечень 25 пользовательских триггеров экспортирован из pg_trigger в `datalogical.json`.

## Конкурентный доступ

1. Бронь, недоступность и сеанс используют одну строку `equipment`.
2. `lock_equipment` выполняет UPDATE счётчика schedule_revision, удерживая блокировку до конца внешней транзакции.
3. В READ COMMITTED конкурентная операция ждёт; последующие SQL-команды VOLATILE PL/pgSQL видят зафиксированные данные.
4. В REPEATABLE READ/Serializable UPDATE изменённой после снимка строки завершается 40001: проверка не продолжается на устаревшем снимке.
5. EXCLUDE дополнительно запрещает пересечение подтверждённых броней, в том числе при прямом INSERT.
6. При ТО после брони AFTER-триггер атомарно меняет будущую бронь на needs_transfer. При ТО перед бронью бронь отклоняется.
7. Перенос блокирует старое и новое оборудование в порядке id и проверяет предложение повторно.
8. Прямой UPDATE брони может взять блокировку самой брони раньше её BEFORE-триггера; при обратном порядке возникает 40P01, а не нарушение данных. Сервер должен повторить **всю** транзакцию при 40P01/40001 с ограниченным числом попыток. В штатном API оборудование блокируется заранее.
9. Длительные внешние транзакции увеличивают ожидание; работа с UI и сетью должна проходить за пределами транзакции.
10. Измерение 100 веб-сессий и NFR-01/NFR-02 не выполнено: backend и окружение Helios ещё отсутствуют.

Это специально не объявлено общим межтабличным EXCLUDE: ограничение booking не контролирует unavailability. Межтабличный инвариант реализован общим ресурсом сериализации и триггерами.
Проверки приложения полезны для объяснения причины отказа, но не заменяют этот протокол.

## API и безопасность следующего этапа

Владелец схемы — миграционная роль; обычная роль backend получает права через `sql/scripts/grant_application.sql`.
В тесте роль NOLOGIN создаётся внутри откатываемой транзакции, без постоянных пользователей/паролей.
Публичные изменяющие функции имеют SECURITY DEFINER; `search_path` всех функций фиксирован: labreserve, pg_catalog, pg_temp.
Backend получает SELECT и EXECUTE только именованного API; прямые изменения расписания и вызов внутренних guard-функций запрещены (T58/T59).
`p_actor`/`p_user` — проверенный идентификатор из аутентифицированного Spring Security-контекста, а не значение, которому можно доверять из тела HTTP-запроса.
Человеческие роли в app_role не являются SQL-ролями PostgreSQL. БД проверяет роли/владение, а достоверность личности обеспечивает будущий backend.
Запрет произвольного DML и фиксированный search_path не защищают от владельца БД/суперпользователя, который может отключить триггеры.
Пароли демонстрационных людей отсутствуют (NULL), вход в систему пока не реализован. Реальный backend обязан использовать Argon2id согласно NFR-04.
Каталог на третьем этапе редактируется административным сервисом; выдачу дополнительных привилегий/обёрток следует согласовать при реализации. Критические операции расписания должны вызывать созданные функции через native JPA-запросы, без Spring JDBC.

## Вариант Helios

Общая SQL-реализация адаптируется в `s466088` с префиксом `lr_`; контракт `labreserve.actor_id` сохраняется. При доступном установленном btree_gist сохраняется EXCLUDE. Без расширения `lr_check_booking` после UPDATE строки оборудования проверяет пересечения с другими confirmed и выдаёт 23P01. VOLATILE обеспечивает новое чтение после ожидания в READ COMMITTED; REPEATABLE READ завершается 40001 при изменённой после снимка строке оборудования. Триггер действует для прямого INSERT/UPDATE, включая несколько строк одного оператора.

Проверены API и прямой DML в двух соединениях, оба порядка ТО/брони и откат первого запроса: `HELIOS_TESTING.md`. Права устанавливаются только на перечисленные `lr_`-объекты, а не на все объекты студенческой схемы. Студенческий владелец сохраняет административные права на собственные объекты; отдельная backend-роль требует участия DBA.
