# Развёртывание «ЛабРезерв» на Helios

## 1. Окружения и требования

| Параметр | LOCAL | HELIOS |
|---|---|---|
| База | `labreserve_stage02_test` | `studs` |
| Схема | `labreserve` | существующая `s466088` |
| Предметные таблицы | 17, исходные имена | 17, префикс `lr_` |
| Установка | `sql/scripts/install.sql` | `scripts/deploy_helios.sh` |
| Проверки | `sql/scripts/run_checks.sh` | `scripts/check_helios.sh` |
| Пересечения броней | EXCLUDE / btree_gist | EXCLUDE при доступном расширении; иначе сериализующий триггер |

На Helios нужны PostgreSQL 14+ (multirange и range_agg), psql с поддержкой `\if`, Python 3.8+, USAGE/CREATE в собственной схеме и TEMP в `studs`. SUPERUSER, CREATEROLE и CREATE в базе не требуются. Если сервер старше по возрасту, чем PostgreSQL 14, preflight завершится ошибкой: текущая модель использует multirange и не устанавливается частично.

В студенческой схеме размещается также служебная таблица `lr_deployment`; она не относится к 17 предметным таблицам. Все функции, домен, индексы, триггеры, явные и автоматически созданные ограничения и последовательности имеют префикс `lr_` (служебные массивные типы PostgreSQL — `_lr_`). Имя настройки сеанса **`labreserve.actor_id` сохраняется**.

На реальном Helios доступен Python 3.11 под именем `python3.11`. Скрипты используют `helios_python.sh`, который выбирает python3, python3.11 или python и проверяет версию; при необходимости можно задать `HELIOS_PYTHON`.

## 2. Диагностика

После входа на Helios:

```bash
psql -X -h pg -U s466088 -d studs
```

```sql
SELECT version();
SELECT current_user, current_database();
SELECT extname FROM pg_extension WHERE extname='btree_gist';
SELECT has_database_privilege(current_database(),'CREATE');
SELECT has_schema_privilege('s466088','CREATE');
```

Автоматическая диагностика дополнительно выводит схему расширения, его доступность на сервере, права USAGE/TEMP и признаки SUPERUSER/CREATEROLE. Отсутствие административных прав — штатная конфигурация. Версия, имя базы, SQL-пользователь и права проверяются до установки:

```bash
bash scripts/deploy_helios.sh preflight
```

Вызов `psql -f sql/helios/preflight.sql` также защищён SQL-проверкой, независимо от проверки параметров в shell. При отказе возвращается ненулевой код.

## 4. Установка на Helios

После SSH-входа:

```bash
mkdir -p ~/labreserve-stage02-20261013
cd ~/labreserve-stage02-20261013
tar -xzf ~/labreserve-stage02-20261013.tar.gz
export PGHOST=pg PGDATABASE=studs PGUSER=s466088
bash scripts/deploy_helios.sh preflight
bash scripts/deploy_helios.sh install
```

Скрипт строит временный SQL-комплект из общих файлов LOCAL. Адаптер разбирает идентификаторы, SQL-литералы, комментарии и тела функций. Переименовываются только известные объекты; сообщения и ключ `labreserve.actor_id` не заменяются как имя схемы. Динамические SQL-вызовы и проверки TG_TABLE_NAME адаптируются отдельно. Общие файлы бизнес-логики не копируются вручную и не редактируются для Helios.

Установка выполняется одной транзакцией под advisory lock. Она не создаёт базу или схему, не устанавливает расширения, не создаёт роли и не меняет права на посторонние объекты. ALTER/REVOKE адресуют исключительно именованные объекты курсовой. Если обнаружены существующие `lr_`-объекты без манифеста, установка отказывается продолжать; ничего не перезаписывается.

DDL, функции, индексы, демонстрационные данные и манифест фиксируются вместе. Ошибка до COMMIT откатывает установку. Проверки после COMMIT используют отдельную транзакцию с ROLLBACK: их ошибка не удаляет уже установленную базу, а возвращает ненулевой код для диагностики.

**На Helios не запускаются** локальные `create_database.sql`, `drop_database.sql`, `clean_schema.sql`, `run_checks.sh` и `grant_application.sql`. Эти скрипты предназначены для изолированного LOCAL-окружения.

## 5. Повторный запуск

```bash
bash scripts/deploy_helios.sh install
```

`lr_deployment` хранит хеш исходников установки, выбранный механизм пересечений, факт загрузки примеров и отпечаток каталога PostgreSQL. При совпадении версии и структуры существующие объекты и данные сохраняются; повторная загрузка примеров не производится. Значения последовательностей и пользовательские данные в отпечаток каталога не входят.

Проверяются определения функций, фиксированный search_path, столбцы, ограничения, индексы, состояние триггеров, владельцы и ACL. Изменённый исходник, отключённый триггер, добавленный посторонний `lr_`-объект или неполный манифест приводят к отказу. Автоматической переустановки и режима удаления нет. Обновление установленной версии требует отдельной адресной миграции после изучения текущих данных; изменение хеша вручную не является миграцией.

## 6. Защита от пересечений и btree_gist

Если `btree_gist` уже установлено и есть USAGE его схемы, используется исходный частичный EXCLUDE GiST. Схема расширения обнаруживается по pg_extension и включается в путь поиска при DDL; `public` не предполагается. Расширение остаётся во владении своего владельца.

Если расширение отсутствует или его схема недоступна, используется вариант без административных привилегий:

1. BEFORE-триггер бронирования выполняет существующий UPDATE `lr_equipment.schedule_revision`.
2. После получения блокировки VOLATILE PL/pgSQL проверяет другие подтверждённые брони того же оборудования и пересечение диапазонов.
3. Пересечение вызывает **23P01**, тот же SQLSTATE, что исходный EXCLUDE; `lr_request_booking` сохраняет прежний контракт.
4. В READ COMMITTED конкурентный запрос ждёт и затем проверяет данные зафиксированной транзакции. При REPEATABLE READ устаревший UPDATE строки оборудования завершается **40001**.
5. Этот триггер действует для API, прямых INSERT/UPDATE и многострочных вставок. Перенос сохраняет блокировку двух единиц оборудования в порядке id; межтабличная сериализация ТО, поломок и сеансов сохраняется.

Смешанные GiST-индексы без расширения заменены GiST по одному диапазону с теми же частичными предикатами; фильтры пользователя/оборудования остаются в запросах. Меняется индексная стратегия, а не предметная модель. Вариант содержит 37 индексов вместо 38: отсутствует индекс EXCLUDE. Тесты не подтверждают показатели веб-нагрузки или производительность на Helios.

При 40001/40P01 вызывающий сервер должен откатить и ограниченно повторить **всю** транзакцию. Владелец схемы может отключить триггеры; защита от действий владельца/DBA не входит в гарантии исходного или адаптированного варианта.

Основания: [изоляция PostgreSQL](https://www.postgresql.org/docs/18/transaction-iso.html), [безопасный search_path функций](https://www.postgresql.org/docs/18/sql-createfunction.html), [btree_gist](https://www.postgresql.org/docs/18/btree-gist.html).

## 7. Автоматические проверки

```bash
bash scripts/check_helios.sh
```

18 smoke-проверок покрывают 17 таблиц, 32 функции, 27 FK, 25 включённых триггеров, каталог и допуски, создание/отмену брони, прямой конфликт, альтернативы и перенос, неисправность и ремонт, сеанс, уведомления, аудит и аналитику. Пробные данные создаются с уникальными метками и откатываются; IDENTITY-последовательности могут продвинуться — PostgreSQL не откатывает выдачу номеров.

Небольшие конкурентные пробы запускаются явно:

```bash
bash scripts/check_helios.sh --concurrency
cat output/helios-concurrency.json
```

Десять сценариев используют два реальных psql-соединения и подтверждают одновременность через наблюдаемое ожидание блокировки в pg_stat_activity. Проверяются API и прямой DML при READ COMMITTED/REPEATABLE READ, конфликт UPDATE, оба порядка ТО/брони, откат первой транзакции и многострочная вставка. Это не нагрузочный тест.

Для доказательства поведения после COMMIT конкурентные пробы фиксируют отдельные объекты с меткой `LR-PROBE-*`. В конце их брони отменяются, ТО отменяется, оборудование/тип архивируются, тестовые пользователи деактивируются. Аудируемая история сохраняется; существующие пользовательские данные не удаляются. Поэтому concurrency не включён в обычную установку и smoke-проверку.

`test_adapter.py` — автономные проверки генератора. `test_installation.py` — административные проверки в **одноразовом локальном кластере**; на Helios их не запускают. Общие 57 бизнес-утверждений собираются в `assertions.sql` для новой локальной симуляции без CREATEROLE. Три исходных проверки отдельных SQL-ролей T58–T60 остаются в полном LOCAL runner; smoke на Helios не выдаёт проверку разных SQL-ролей за выполненную.

## 9. Ошибки и действия

| Сообщение | Действие |
|---|---|
| SSH Permission denied | Войти своим действующим ключом/паролем; проверить пользователя и порт 2222. Пароль в проект не добавлять. |
| PostgreSQL authentication failed | Проверить личные учётные данные для pg/studs/s466088 и доступность pg из Helios. |
| Only studs / s466088 allowed | Исправить PGDATABASE/PGUSER; не обходить проверку. |
| Helios check refused | Прочитать preflight: версия 14+, существующая схема, CREATE/USAGE и TEMP. |
| Existing lr_ objects without deployment marker | Изучить эти объекты; не удалять схему и не запускать LOCAL cleanup. |
| source changed / modified objects | Сравнить установленный комплект и определения; подготовить адресную миграцию. |
| lock timeout | Завершить зависшие собственные операции и повторить; чужие соединения не завершать. |
| 23P01 / 23514 | Пересчитать доступность и варианты; это бизнес-отказ. |
| 40001 / 40P01 | ROLLBACK и ограниченный повтор всей транзакции. |
| нет btree_gist | Штатно выбирается trigger-вариант; CREATE EXTENSION самостоятельно не выполняется. |

## 10. Подключение будущего backend

На Helios datasource внешнего WildFly использует URL `jdbc:postgresql://pg:5432/studs`, пользователя `s466088` и пароль вне репозитория. Это JDBC-драйвер Hibernate; Spring JDBC не используется. Имена JPA-таблиц задаются как `@Table(name="lr_booking", schema="s466088")` и аналогично остальным сущностям; схема по умолчанию — `s466088`. Автоматическое изменение DDL через Hibernate отключается, допустима проверка `validate` после настройки типов PostgreSQL.

Критические операции вызываются через native JPA:

```sql
SELECT s466088.lr_create_booking(:user_id,:equipment_id,:capability_id,:start_at,:end_at,:purpose);
SELECT s466088.lr_cancel_booking(:actor_id,:booking_id,:reason);
SELECT * FROM s466088.lr_find_alternatives(:user_id,:equipment_id,:capability_id,:period);
```

Идентификатор actor приходит из Spring Security. Вызов и фиксация выполняются в одной сервисной транзакции. Отдельная backend SQL-роль, если её предоставляет DBA, должна получать только адресные права на `lr_`-объекты. Студенческий пользователь владеет объектами и технически имеет прямой DML; проверка разных SQL-ролей без CREATEROLE не имитируется.

Для разработки вне Helios можно использовать SSH-туннель:

```bash
ssh -p 2222 -N -L 127.0.0.1:15432:pg:5432 s466088@helios.cs.ifmo.ru
```

Тогда URL datasource — `jdbc:postgresql://127.0.0.1:15432/studs`. Архитектура WAR/WildFly/JPA не меняется; Java-приложение в этом задании не создавалось.
