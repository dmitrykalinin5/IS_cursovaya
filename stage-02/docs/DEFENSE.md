# Как показать второй этап преподавателю

## Что открыть перед защитой

1. `ER-модель_final.drawio.xml` — согласованная инфологическая модель в каталоге `stage-02`: 13 сущностей, 20 связей, две M:N.
2. `diagrams/logical.xml` — даталогическая модель с той же расстановкой 13 блоков, что и на согласованной схеме, плюс две таблицы M:N. Служебные журналы описаны в словаре данных.
3. `report.pdf` — итоговый отчёт. Полный перечень полей и ограничений — в приложении.
4. Терминал с psql. Команды далее выполняются из папки `stage-02`.

Инфологическая модель описывает предметную область. Даталогическая показывает, как эта модель реализована таблицами. Объяснение количества таблиц: 13 сущностей + 2 таблицы M:N + 2 служебных журнала = 17. История и статистика нужны по требованиям первого этапа; в согласованную инфологическую модель они не добавлены.

## Порядок показа на 10–15 минут

| Что показать | Что объяснить |
|---|---|
| Согласованная модель, 1–2 минуты | Тип объединяет аппараты; допуск относится к типу; бронь связывает пользователя, аппарат и требуемую функцию |
| Две M:N | Пользователь может совмещать роли; тип поддерживает несколько функций, функция доступна разным типам |
| Даталогическая модель, 2 минуты | M:N раскрыты через user_role и type_capability; PK идентифицируют строки, FK запрещают неверные ссылки |
| DDL и триггеры, 2 минуты | NOT NULL, UNIQUE, CHECK; интервалы [начало, конец); пересечение броней; контроль допуска и технических событий |
| Живой сценарий, 4–6 минут | Бронь → поломка → техническое событие → предложение переноса → выбор → ремонт; отдельно фактический сеанс |
| Индексы и тесты, 1–2 минуты | GiST для диапазонов, B-tree для ссылок и истории; реальные проверки и два одновременных соединения |

Техническое событие хранит факт ТО или подтверждённой неисправности, его интервал, причину и статус. Техническая работа хранит вид выполненной работы, исполнителя и результат. Сообщение пользователя само по себе ещё не подтверждает поломку.

## Подключение к Helios

На своём компьютере:

```bash
ssh -p 2222 s466088@helios.cs.ifmo.ru
```

После входа:

```bash
cd ~/labreserve-stage02-20261027
psql -X -h pg -U s466088 -d studs
```

Пароли вводятся в запросе терминала. В psql:

```sql
\pset pager off
SET TIME ZONE 'Europe/Moscow';
SET search_path=s466088,pg_catalog;
\conninfo
\dt s466088.lr_*
\d s466088.lr_booking
\d s466088.lr_repair
\df s466088.lr_*
```

Названия на Helios имеют префикс `lr_`, например `lr_booking`. Таблица `lr_deployment` — дополнительный манифест установки; она не входит в 17 таблиц модели.

## Живой показ в psql

Всё уже подготовлено на Helios. Для запуска:

```bash
psql -X -h pg -U s466088 -d studs
```

Внутри psql:

```sql
\i output/helios-approved/defense.sql
```

Скрипт печатает семь этапов и проверяет ожидаемое поведение. Он использует учебные учётные записи `student`, `tech`, `novice`, аппарат `FDM-002` и функцию «Печать PLA». Они присутствуют в seed; скрипт ищет их по именам, а не по номерам.

1. Показать каталог, состояние оборудования и допуски.
2. Создать будущую бронь. Повторное пересечение возвращает `23P01`, отсутствие допуска — `23514`.
3. Создать сообщение о неисправности, затем подтвердить техническое событие от имени техника. Бронь получает `needs_transfer`.
4. Показать предложения, явно выбрать одно. Бронь становится `confirmed` на другом аппарате.
5. Закрыть техническое событие. Появится техническая работа с `work_kind=repair`, аппарат станет доступен.
6. Создать короткую текущую бронь, открыть и закрыть фактический сеанс. Повторное закрытие запрещено.
7. Показать уведомления, аудит и аналитику.

Для показа с остановками откройте `output/helios-approved/defense.sql` в редакторе и вставляйте блоки последовательно в **один и тот же сеанс psql**: переменные, созданные `\gset`, живут в этом соединении. Начальный `BEGIN` и конечный `ROLLBACK` сохраняйте. Успешные шаги печатают `PASS`; ожидаемые отказы перехватываются и не ломают транзакцию.

Все демонстрационные изменения отменяются в конце. Номера ID могут иметь пропуски — последовательности PostgreSQL не откатываются. Если исходное оборудование уже занято текущим реальным сеансом или изменены учебные данные, сначала проверьте календарь: не отменяйте чужие записи ради демонстрации.

```sql
SELECT id,equipment_id,period,status FROM s466088.lr_booking ORDER BY id DESC LIMIT 10;

SELECT work_kind,period,result FROM s466088.lr_repair ORDER BY id DESC LIMIT 10;

```

### Если терминал «завис»

- `studs=>` — можно вводить новую команду.
- `studs->` — не закончена команда: обычно не хватает `;`. `\r` очищает текущий ввод.
- `studs=!>` — транзакция прервана ошибкой: выполните `ROLLBACK;`, затем начните сценарий заново.
- Если не закрыта кавычка и команда не принимается — `Ctrl+C`, затем при необходимости `ROLLBACK;`.
- Экран результатов с `(END)` — нажмите `q`; `\pset pager off` отключает постраничный просмотр.
- `\q` — выйти из psql в оболочку; SSH, Python и bash-команды выполняются в оболочке.

## Локальный показ на Fedora

Подготовка отдельного учебного кластера описана в `README.md`. После установки и seed:

```bash
export PGHOST=/tmp PGPORT=55432 PGDATABASE=labreserve_stage02_test
psql -X -f sql/demo/defense.sql
```

Чтобы доказать воспроизводимость и конкуренцию на отдельной тестовой БД:

```bash
bash sql/scripts/run_checks.sh
```

Скрипт пересоздаёт учебную схему, выполняет 60 основных и 4 дополнительных утверждения, 5 конкурентных сценариев и EXPLAIN. На общей базе Helios вместо него используется `scripts/check_helios.sh`.

## Как показать следующие этапы проекта

Этап 3: диаграмма классов → вызов репозитория через JPA/Hibernate → вызов существующей PL/pgSQL-функции → изменение БД. Те же сценарии бронирования и поломки повторяются через бизнес-сервисы; SQL-логику нельзя заменять копией в Java.

Этап 4: те же действия через интерфейс React: вход, выбор аппарата и интервала, бронь, сообщение о неисправности, действия техника, перенос и завершение работы. Сейчас Java/backend и интерфейс ещё не реализованы; для второго этапа достаточно моделей, SQL и psql.
